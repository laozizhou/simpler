A5 上三种调度器的实测对比

同一张卡、同一份 kernel、同一个 1000 任务的图，只换调度方案。结论是拉取式的 topo_queue 在真机上比 HBG 常驻调度器慢 5.8 倍，瓶颈是单队头的串行认领。

bgemm · 1000 tasks · 96 cores (32 AIC + 64 AIV) · A5 card 3 · 2026-09-30

05队头为什么是瓶颈

bgemm 的 500 个 GEMM 全无依赖，开局就该全部可跑。但 topo_queue 的 AIC 核一开始大量闲着。原因在认领记录里看得很清楚。

时间段 µs认领次数平均间隔 µs

认领顺序严格等于 task id 顺序，1000 个无一例外，间隔全程恒定在 3.07 µs（p10 1.63 / p50 2.93 / p90 4.82）。全程平均只有 6.6 个核在真正执行，其余约 89 个核在空转等队头。

任务按 GEMM, ADD, GEMM, ADD… 交错提交，所以 500 个无依赖的 GEMM 坐在 0, 2, 4, 6… 这些位置上。一个 AIC 核想拿到 index 2，必须先有 AIV 核把 index 1 的 ADD 认领走——队头只能一格一格推进，「绝不跳过」是死锁自由证明的前提，跳过的下标没人执行。于是 t=100 µs 时全场只发出去约 33 个任务，而 resident 在 535 µs 内跑完了全部 1000 个。

下一个要认领的队头停留该类型空闲核
AIC 任务3.564 µs27 / 32
AIV 任务2.580 µs62.5 / 64

停留时间随「有多少同型核在轮询」变化，所以这是对一条 cache line 的争抢。纯粹的 GM 往返延迟不会有这个依赖关系。两点拟合出 停留 ≈ 1.8 µs + 47 µs / 轮询核数：一个只有两次读的循环要 47 µs 才转回来，说明这条线已经被 96 个核挤爆——每个核每一圈都要作废并重读同一个队头和同一个 run-control 字。

两次减少轮询的尝试从相反方向都失败了，这正是卡在饱和点的特征：把每圈变便宜（error 轮询采样）让核转得更快、这条线更热，慢 18%；让核少转（异类型退避）则该认领的核发现得更晚，慢 23%。出路只有减少每条队头上的争抢者，也就是增加队头数量——双队列把 96 个争抢者拆成 32 和 64，而且两条链并行推进；每 cluster 一条队头则基本就是 resident 的结构了。

06调度开销分析

仓库自带的 sched_overhead_analysis：某一时刻只要「有空闲核」且「有已就绪但未派发的任务」，就算调度开销。

方案makespanAIC 开销AIV 开销判定
resident535.7 µs0.0%89.9%SCHEDULER-BOUND
legacy831.0 µs0.0%94.8%SCHEDULER-BOUND
topo_queue3110.9 µs0.0%0.0%指标不适用

topo_queue 那个 0% 不能读成「没有开销」。这个指标测的是「就绪」到「派发」之间的空档，而 topo_queue 的派发就是核自己认领——认领往往发生在就绪之前（先占核再等前驱），空档为负，于是指标读数为零。它是为推送式调度设计的，量不到拉取式的病症。同一批数据里，topo_queue 的核有 93.2% 的时间没在算，这才是它的开销。

另一边也值得注意：两种 HBG 模式的 AIV 都饿着（89.9% 和 94.8%）。bgemm 的 AIC 任务是关键路径，AIV 只能等——这是图的形状决定的，不是调度器的错。

07端到端的阶段拆解

设备上慢 5.6 倍，端到端只慢 13%。因为这个测试每轮都重新建图，而 host 建图要 10 ms，占了六成——把设备上的差距稀释掉了。如果图建一次反复执行（推理解码就是这样），建图被摊薄，5.6 倍就会原样变成端到端的差距。

还有一笔冤枉钱：topo_queue 的 publish_image 比 legacy 多花约 600 µs。它并不使用常驻调度器，但为了从 bootstrap context 里取一个图地址，必须跑在 resident 模式下，于是 host 每轮都上传一整份它从不读取的 SchedulerState。

08结论

  • 把调度搬到 AICore 是对的方向。resident 比 legacy 快 2.2 倍，两者解依赖逻辑相同，区别只是调度器从 AICPU 挪到了 AIV 上。
  • topo_queue 慢，不是因为调度在 AICore 上，而是因为只有一个队头。它同样跑在 AICore 上却慢 5.9 倍，甚至比 AICPU 调度的 legacy 还慢 2.7 倍。resident 有 32 个 cluster 调度器并行派发，topo_queue 所有核抢同一条 cache line，每 3.6 µs 才能发出一个任务。
  • 先认领后等前驱另有代价。每个任务平均占着核空等约 16 µs，接近它占用核时间的一半。核数充足时被并行掩盖，核数紧张时会直接暴露。
  • 仿真结论完全反转。仿真里 topo_queue 快约 3 倍，真机上慢 5.7 倍。仿真的 dcci 是全内存栅栏、没有真实 GM 延迟、24 线程超订在约 10 个 host 核上，压不出 96 核的队头争抢。

下一步最直接的是双队列（AIC、AIV 各一个头），两条链并行，乐观估计能到约 1.6 µs/task，落在 legacy 和 resident 之间；要追平 resident 则需要把队头数做到 cluster 量级。双队列消不掉那 16 µs 的等前驱。
